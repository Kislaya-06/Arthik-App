# Daily budget of ₹500 is treated as a sentinel value, causing silent row deletion

Status: needs-triage

## Description

In `src/store/dailyBudgetStore.ts`, a budget value of exactly `500` is hardcoded as a sentinel value representing corrupted or fake data. This was originally introduced to purge phantom rows generated by a historical 35-day backfill loop and an OTA update bug where user profiles received a database default budget of 500.

However, because `500` is also a normal, valid daily budget amount that real users configure, treating `500` as a sentinel causes `hydrateFromSupabase` to misidentify legitimate user savings logs as phantom records and delete them from Supabase.

The sentinel treatment of 500 occurs in four specific locations:

1. **`isPhantom500Day` Deletion Check (lines 976–990)**:
```typescript
// src/store/dailyBudgetStore.ts:976-990
const isPhantom500Day =
  daySpent === 0 &&
  !spentByDate[d] &&
  (rawLogBudget === 500 || rawLogSaved === 500) &&
  (!records[d] || records[d].budget === 500 || records[d].budget === 0) &&
  (d !== yesterdayStr || !resolvedAutoRenew || resolvedBudget <= 0);

if (isPhantom500Day) {
  // Delete phantom row from Supabase and purge from local records
  supabase.from('daily_savings_log').delete().eq('user_id', userId).eq('date', d).then(() => {});
  if (records[d]) {
    delete records[d];
  }
  continue;
}
```

2. **Budget Resolution Guard on Supabase Log (line 995)**:
```typescript
// src/store/dailyBudgetStore.ts:994-997
if (rawLogBudget !== null && rawLogBudget > 0 && rawLogBudget !== 500) {
  // Explicit custom budget saved for this day
  dayBudget = rawLogBudget;
}
```

3. **Budget Resolution Guard on Local Store Record (line 998)**:
```typescript
// src/store/dailyBudgetStore.ts:997-999
} else if (records[d]?.budget && records[d].budget > 0 && records[d].budget !== 500) {
  // Local store has the real custom budget
  dayBudget = records[d].budget;
}
```

4. **Budget Resolution Guard on User Profile Budget (line 1000)**:
```typescript
// src/store/dailyBudgetStore.ts:999-1002
} else if (resolvedBudget > 0 && resolvedBudget !== 500) {
  // User's daily budget is non-500 (e.g. 100) -> The 500 in the log was the fake DB default!
  dayBudget = resolvedBudget;
}
```

## Origin in Git History

The 500 sentinel logic was introduced across two commits attempting to remediate phantom records and an OTA update corruption:

### 1. The Original Backfill Bug:
In commit `d375bc2` ("Optimised Code"), an automated 35-day backfill loop was added to `checkAndRollover`:
```typescript
// Commit d375bc2 in src/store/dailyBudgetStore.ts:
if (get().isAutoRenew) {
  const earliestDateStr = userCreatedAtStr || format(subDays(new Date(), 30), 'yyyy-MM-dd');
  let fillCursor = subDays(new Date(), 1);
  let safetyCount = 0;
  while (safetyCount < 35) {
    const dStr = format(fillCursor, 'yyyy-MM-dd');
    if (dStr < earliestDateStr) break;
    pastDates.add(dStr);
    fillCursor = subDays(fillCursor, 1);
    safetyCount++;
  }
}
```
Because `profiles.daily_budget` and `daily_savings_log.budget_amount` had previously defaulted to `500` in SQL migrations, this loop generated up to 35 synthetic historical days with `budget = 500`, `spent = 0`, and `saved = 500` for dates before the user ever opened the app.

### 2. Commit `63a79dd`:
```

```
This commit added the initial self-healing heuristic to infer a user's original budget if their profile had been reset to the migration default of 500.

### 3. Commit `010ea38`:


## Consequence Traces: ₹500 User vs ₹300 User

To demonstrate the real-world consequence, we trace both a user with a ₹500 budget and a user with a ₹300 budget through `hydrateFromSupabase` for a legitimate past day where they spent ₹0.

### Scenario Setup:
- Date being evaluated: `d = '2026-09-15'` (3 days ago; `d !== yesterdayStr`).
- Both users have `is_auto_renew: true` on their profile.
- On `2026-09-15`, neither user spent any money (`spentByDate['2026-09-15'] = undefined`).
- Both users have an existing, confirmed record in Supabase `daily_savings_log` with `amount_saved = budget`, `spent_amount = 0`, `status = 'saved'`.

---

### Trace 1: User with Daily Budget = ₹500

1. **Profile Resolution (lines 835–870)**:
   - Remote `profileData.daily_budget` is `500`.
   - Line 851 checks `if (remoteBudget === 500)`. It leaves `resolvedBudget = get().dailyBudgetAmount` (which is `500`).
   - `resolvedAutoRenew = true`.
2. **Historical Log Ingestion (line 958)**:
   - Loop reaches log entry for `d = '2026-09-15'`.
   - Line 965: `rawLogBudget = 500`.
   - Line 966: `rawLogSaved = 500`.
   - Line 967–972: `daySpent = 0` (from `log.spent_amount === 0`).
3. **`isPhantom500Day` Evaluation (lines 976–981)**:
   - `daySpent === 0` $\rightarrow$ **`true`**
   - `!spentByDate[d]` $\rightarrow$ **`true`** (zero expenses recorded)
   - `(rawLogBudget === 500 || rawLogSaved === 500)` $\rightarrow$ **`true`** (`500 === 500`)
   - `(!records[d] || records[d].budget === 500 || records[d].budget === 0)` $\rightarrow$ **`true`** (`records[d].budget` is `500`)
   - `(d !== yesterdayStr || !resolvedAutoRenew || resolvedBudget <= 0)` $\rightarrow$ **`true`** (since `d` is 3 days ago, `d !== yesterdayStr` is `true`)
   - $\Rightarrow$ `isPhantom500Day` evaluates to **`true`**.
4. **Execution of Deletion Block (lines 983–990)**:
   - Line 985 executes:
     ```typescript
     supabase.from('daily_savings_log').delete().eq('user_id', userId).eq('date', d).then(() => {});
     ```
     **The user's legitimate row in Supabase is permanently DELETED.**
   - Line 986–988:
     ```typescript
     if (records[d]) {
       delete records[d];
     }
     ```
     **The record is purged from local store memory.**
   - Line 989 calls `continue`, skipping budget resolution and metric calculation for this date.
   - Lines 1058–1073 execute a secondary local cleanup loop that also deletes any matching record with `r.budget === 500 && r.saved === 500`.

**Result for ₹500 User**:
The user's legitimate saved day is completely erased from both remote Supabase storage and local AsyncStorage. Their ₹500 savings credit for that day is deducted from `totalAccumulatedSavings`, and because the day is deleted from `records`, the consecutive loop in `calculateSavingsMetrics` encounters a missing record and **breaks the user's savings streak**.

---

### Trace 2: User with Daily Budget = ₹300

1. **Profile Resolution (lines 835–870)**:
   - Remote `profileData.daily_budget` is `300`.
   - Line 847: `remoteBudget !== 500`, so `resolvedBudget = 300`.
   - `resolvedAutoRenew = true`.
2. **Historical Log Ingestion (line 958)**:
   - Loop reaches log entry for `d = '2026-09-15'`.
   - Line 965: `rawLogBudget = 300`.
   - Line 966: `rawLogSaved = 300`.
   - Line 967–972: `daySpent = 0`.
3. **`isPhantom500Day` Evaluation (lines 976–981)**:
   - `daySpent === 0` $\rightarrow$ `true`
   - `!spentByDate[d]` $\rightarrow$ `true`
   - `(rawLogBudget === 500 || rawLogSaved === 500)` $\rightarrow$ **`false`** (`300 === 500` is `false`)
   - $\Rightarrow$ `isPhantom500Day` evaluates to **`false`**.
4. **Execution of Deletion Block (lines 983–990)**:
   - The deletion block is **SKIPPED**.
5. **Budget Resolution (lines 994–1007)**:
   - Line 994: `rawLogBudget !== null && rawLogBudget > 0 && rawLogBudget !== 500` is **`true`** (`300 > 0 && 300 !== 500`).
   - `dayBudget` resolves to `300`.
6. **Recalculation & State Retention (lines 1010–1029)**:
   - `daySaved = Math.max(0, 300 - 0) = 300`.
   - `evaluatedStatus = 'saved'`.
   - `records['2026-09-15']` is set with `budget: 300, spent: 0, saved: 300, status: 'saved', isFinalized: true`.
7. **Secondary Cleanup (lines 1058–1073)**:
   - `r.budget === 500` is `false` (budget is 300), so the record is not deleted.

**Result for ₹300 User**:
The user's row in Supabase remains untouched. The day is properly loaded into local state as `saved` with ₹300 savings, and their savings streak continues uninterrupted.

---

## Summary of Defect

Treating `500` as a sentinel value causes asymmetric data loss: any user who legitimately chose ₹500 as their daily budget will have past zero-spending days (days other than yesterday) silently deleted from the Supabase database and purged from local memory on every launch.
